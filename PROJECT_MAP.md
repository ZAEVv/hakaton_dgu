# Карта проекта для ИИ-агента

Актуальное назначение: веб-система колледжа для сообщений о неисправностях и безопасных типовых вопросов. Подать заявку можно без аккаунта с секретной ссылкой и трёхзначным кодом отслеживания либо с аккаунтом. Заявитель общается с помощником, тот классифицирует сообщение и готовит краткое описание; заявка попадает в панель УПК после выбора места. Сотрудник обрабатывает её, а заявитель видит статус и публичные ответы. Официальное ТЗ хакатона предоставляется пользователем отдельно; при конфликте уточняйте требования по актуальному документу и запросу пользователя.

## Запуск и конфигурация

Из корня проекта: создать `.venv`, установить `pip install -r assistant/requirements.txt`, запустить `python assistant/setup_env.py` для создания локального `.env`, только если его ещё нет, и при необходимости вручную задать `DEEPSEEK_API_KEY`. Для локального HTTP нужен `SESSION_COOKIE_SECURE=0`; для HTTPS — `1`. `python assistant/bootstrap_rooms.py` инициализирует базу и добавляет 36 кабинетов без аккаунтов; отдельно `flask --app assistant/main create-admin` создаёт администратора. `python assistant/seed.py` отдельно создаёт демонстрационные данные и аккаунт. `python assistant/main.py` вызывает `init_db()` и запускает Flask. Инструкция и оговорки приведены в `assistant/README.md`.

`load_dotenv(BASE / '.env')` не перезаписывает уже существующие переменные окружения. `DATABASE` и `UPLOAD_DIR` относительны к `assistant/`. `TRUSTED_HOSTS` ограничивает допустимые имена хостов. `DEEPSEEK_MODEL` по умолчанию `deepseek-flash`; реально используется `DEEPSEEK_API_KEY`, а не резервное поле `API_KEY`. `DEEPSEEK_DEMO_KNOWLEDGE=1` включает только явно помеченные демонстрационные инструкции. Не показывайте значения конфигурации и ключи пользователю или в логах.

`flask --app assistant/main run` сам по себе не вызывает `init_db()`; сначала нужна инициализация. Встроенный Flask-сервер предназначен для разработки, а не публичной эксплуатации. Для телефона нужен доступный ему адрес и разрешённый host; QR-код формируется из текущего адреса сервера.

## Основной сценарий заявителя

1. `GET /` доступен без входа и с аккаунтом; регистрация `/account/register`, выход `POST /account/logout`. Сессия аккаунта проверяется по хешу токена в `applicant_sessions` и имеет предел 12 часов.
2. QR открывает `/?room=<id>`. При необходимости идентификатор сохраняется в сессии до входа/регистрации; затем проверяется по таблице `rooms` и подставляется в форму. Неизвестный идентификатор не принимается как место.
3. `index.html` включает чат `ai_assistant.html` и ручную форму в раскрывающемся блоке. JS отправляет текст в `POST /api/assistant`; если информации не хватает, собирает последующие сообщения. Текст в запросе может содержать личные сведения, введённые пользователем, и передаётся DeepSeek.
4. Помощник распознаёт тип, предлагает категорию и короткое описание. При опасных признаках локальная проверка немедленно показывает предупреждение; после выбора места опасное обращение тоже можно отправить. Если формирование краткого опасного описания недоступно, используется сообщение о проблеме.
5. После распознавания неисправности и выбора существующего места чат отправляет стандартную форму `POST /`. Для места из QR отправка может начаться сразу. Фото можно выбрать в чате до сообщения или в ручной форме; оно передаётся с заявкой, не нейросети. `request_key` (UUID v4) и уникальность в `ticket_access` обеспечивают идемпотентность; повтор другого заявителя не раскрывает заявку.
6. Сервер валидирует корпус, помещение, категорию, описание и фото, записывает заявку, публичное событие создания, ключ запроса и при необходимости вложение в транзакции. После коммита перенаправляет владельца на `/account/tickets/<id>`, а анонимного заявителя на `/track/view`. Для последнего выдаются секретная ссылка и трёхзначный код; повторное открытие через POST `/track`. Ссылку и код надо сохранить и не раскрывать. Чат показывает номер только после подтверждения сохранения.
7. Чат до создания заявки хранится в `sessionStorage` конкретной вкладки, с ключом по ID заявителя или для анонимного режима; код также может сохраняться в истории чата вкладки. Это не серверное долговременное хранилище. После создания заявки сервер хранит историю и публичную переписку. Не раскрывайте внутренние записи в интерфейсе заявителя.

`GET /account` — список только своих заявок. `/account/tickets/<id>` проверяет владельца, показывает статус, описание, место, публичные комментарии и безопасно выделенные изменения статуса. Заявитель может отвечать на незакрытую заявку, но не меняет статус. Фото выдаются по `/account/attachments/<id>` только владельцу; анонимные фото через `/track/attachments/<id>` после проверки кода. Старый `/ticket/<token>` возвращает 410: исторические заявки без владельца доступны сотрудникам, автоматически привязывать их к новым аккаунтам нельзя.

## ИИ и безопасность ответов

`POST /api/assistant` доступен с аккаунтом и без него, требует заголовок `X-CSRF-Token`. Проверяет длину текста до 2000 символов, учитывает лимиты 10 запросов в минуту и 60 в час на аккаунт или IP анонимного пользователя, 300 в час на сервер суммарно. Локальная проверка опасных признаков имеет исключение из лимита для немедленного предупреждения; отдельная попытка ИИ-сокращения опасной заявки учитывается в лимите. Ограничения и локальные правила не гарантируют обнаружение всех опасных формулировок.

`assist()` в `ai_helper.py` использует серверный HTTPS-запрос `/chat/completions`, модель из настройки и JSON-ответ. Он передаёт текст обращения, проверенное выбранное место, названия категорий и заголовки проверенных записей, а не фото или поля аккаунта автоматически. Модель выбирает `question`, `fault`, `unclear` или `danger`, категорию и запись знаний; для неисправности предлагает краткое `summary`. Сервер проверяет формат, допустимую категорию, существование ID источника и длину описания. Проверка формата не доказывает фактическую правильность сводки: модель может добавить неверные сведения. Ответ на вопрос берётся из записи `knowledge_base` с `is_verified=1`, а не из свободного текста модели; при отсутствии записи — сообщение о нехватке проверенных данных. База может содержать до 30 выбранных записей в запросе. Локальная фильтрация паролей и опасных слов — дополнительные меры, не абсолютные гарантии.

Опасные запросы получают фиксированный текст без ожидания сети. При `summarize_danger=true` ИИ может подготовить краткое описание после предупреждения; при неудаче чат использует исходное сообщение. ИИ не меняет статусы, не назначает исполнителя и не закрывает заявку. Чат пользователя автоматически отправляет заполненную заявку в установленных условиях; не путайте эту функцию с правом модели выполнять административные действия.

## Панель сотрудника

- `GET/POST /login`, `POST /logout`: отдельная сессия, `employee_sessions`, проверка активности и срока на защищённых маршрутах. Вход заявителя и сотрудника в одном браузере переключает текущую роль.
- `GET /admin`: список всех заявок, поиск и фильтры, показатели всего/открыто/решено. Открыты все статусы кроме `Решена`, старого `Закрыта` и `Отклонена`.
- `/admin/tickets/<id>`: карточка; администратор меняет любую, исполнитель — назначенную ему. Проверяется версия записи для предотвращения перезаписи при конкуренции. При решении и отклонении нужен публичный итог или причина. Кнопка принятия устанавливает `В работе`, назначает ответственного при необходимости и добавляет публичный ответ.
- `/admin/tickets/<id>/claim`: сотрудник берёт свободную незакрытую заявку. `/admin/attachments/<id>` выдаёт вложение вошедшим сотрудникам; сейчас исполнители видят все заявки и фотографии, а не только назначенные.
- `/admin/employees`: администратор создаёт и блокирует исполнителей, сбрасывает пароль; действия в `employee_history`, сессии отзываются. `/admin/applicants/<id>` показывает данные заявителя и его заявки сотруднику.
- `/admin/qr`, `/admin/qr/<id>.png` и `/admin/qr/all.zip`: только администратор управляет местами и скачивает PNG-коды по одному или общим архивом с перечнем помещений. QR содержит ID места и адрес сервера, без персональных данных.

Семь состояний: `Новая`, `На рассмотрении`, `Назначен исполнитель`, `В работе`, `Нужны уточнения`, `Решена`, `Отклонена`. Переходы не принуждаются к строгой последовательности; история записывает изменения. Проверяйте публичные и внутренние комментарии, особенно когда запись содержит и изменение статуса, и закрытый текст.

## Данные и ограничения

- `rooms` — корпус и имя места; `knowledge_base` — вопрос, ответ и проверенность.
- `employees`, `applicants`, `employee_sessions`, `applicant_sessions`, `employee_history` — аккаунты, сессии и аудит сотрудников. Поле заявителя `record_book` фактически используется как логин.
- `tickets` — номер `id`, владелец, описание, категория, место, статус, исполнитель, время и версия. `ticket_history` — изменения и комментарии с признаком `is_public` и автором.
- `attachments` — путь к файлу; проверяется, что он находится внутри `UPLOAD_DIR`. Новые JPEG/PNG/WebP проверяются и пересохраняются без метаданных, ограничены по размеру и разрешению. Старые фото не очищаются автоматически.
- `ticket_access` — исторические токены и уникальные ключи повторной отправки; токен больше не предоставляет доступ. `assistant_requests` и `login_attempts` используются для лимитов.
- `anonymous_ticket_access` содержит хеши ранее выданных длинных кодов; новые ссылки и PIN хранятся только в виде хеша токена и HMAC пары в `anonymous_ticket_pin_access`. `anonymous_pin_attempts` ограничивает попытки на заявку; `anonymous_assistant_requests` ограничивает запросы по хешу IP. Секрет ссылки находится во фрагменте URL и с PIN передаётся в теле POST; пара хранится в подписанной cookie сессии (cookie не шифруется). Не записывайте тела запросов или cookie в журналы. После замены SECRET_KEY новые пары ссылка/PIN перестанут работать. Для их восстановления механизма нет.
- SQLite, `.env`, старый `api.env`, загрузки и виртуальное окружение исключены из Git. Бэкап приложения включает согласованную копию базы и фото. Рабочая база может отличаться от демонстрационной схемы; миграции должны быть безопасны и обратимы.

Известные ограничения: открытая самостоятельная регистрация не подтверждает личность; восстановления пароля заявителя нет; исполнители видят общий журнал; нет оповещений, внешнего развёртывания, гарантии фактической точности ИИ или полноценной защиты от любого злоупотребления; лимиты по IP требуют корректной настройки прокси. В README описаны рекомендации и пределы системы. Не считайте локальные демонстрационные пароли пригодными для реальной эксплуатации.

## Проверка перед сдачей

```bash
.venv/bin/python -m unittest discover -s assistant -p 'test_*.py' -v
node --check assistant/static/ai-assistant.js
node --check assistant/static/ticket-form.js
```

Проверить отдельно полный путь: QR → вход/регистрация → сообщение → уточнение/место → заявка → поиск сотрудником → назначение и публичное принятие → статус/ответ в аккаунте. Проверить опасный запрос и ручную форму при ошибке API, чужую заявку и фото, повторную отправку, размер/тип файла, неверный QR и защиту панели. Для проверки DeepSeek необходим действующий ключ и доступный сервис; не печатать ключ и не тестировать с чужими персональными данными. Проверить QR обычной камерой смартфона в той же сети. Внешний API, браузер, мобильные устройства и тесты — отдельные виды проверки: не объявляйте их успешными без фактического выполнения.
